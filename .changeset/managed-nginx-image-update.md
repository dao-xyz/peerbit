`peerbit domain configure` and `peerbit domain lease claim` now start the managed NGINX and Certbot container from `jonasal/nginx-certbot:6.2.0-nginx1.31.9`, pinned by digest, instead of `6.2.0-nginx1.31.2`. This moves NGINX from 1.31.2 to 1.31.9 and Certbot from 5.6.0 to 5.10.0, and brings in the NGINX security fixes released in 1.31.3 through 1.31.9. Among them is the fix for CVE-2026-118899 (infinite loop while reading client request body over TLS 1.3). The managed configuration uses the setup that advisory names, `listen` with `ssl` in the `http` block and TLS 1.3 enabled, on ports 443, 4003 and 9002. NGINX 1.31.10 had no `jonasal/nginx-certbot` build when this image was chosen; its one security fix, CVE-2026-132779 (excessive CPU usage in TLS 1.3 with `ssl_early_data`), applies only with `ssl_early_data on`, which the managed configuration does not set. The NGINX configuration Peerbit writes is unchanged, but NGINX 1.31.9 now rejects header lines without a colon and chunked request bodies with too much framing overhead.

Existing domains keep running their current container, on the image it was created from, until the domain is configured again; updating or restarting the server does not replace it. To move a domain to the new image, run `peerbit domain configure` for it again on the server, as in the setup guide (`sudo peerbit domain configure node.example.com --email you@example.com --wait`). For a managed DNS lease, pass the leased domain name: running `peerbit domain lease claim` again does not reconfigure a lease that is already configured. With the default `--wait`, the previous container is kept as a rollback backup until the new one passes the HTTPS readiness check; `--no-wait` skips that check and removes the backup once the new container is running. HTTPS is briefly unavailable while the container restarts.
