SQLite iterators no longer page with OFFSET. Short reads stay cheap: a search over one root table, without a child table or an Or of two or three terms in its query (and, when sorted, over rows without a child table), reads its first page with one statement and one extra row (which tells whether more remain), and in primary-key order the next pages continue after the last key returned, while nothing is written or marked, for up to 2,048 rows. Every other read lists the keys of the matching rows once, in the search's order with the primary key as the tiebreak, and reads each page's rows by key. After rows change between two calls, each call re-checks only the changed rows (an iterator that was reading by pages first lists the keys of all matching rows once), instead of reading every earlier row again on each page. Each call (`next`, `pending`, `all`) runs in one database admission, so a delete that was queued before the next page can no longer make that page skip a live row. Also:

- `done()` is true right after the call that returns the last row, without one more empty call, and it is `false` rather than `undefined` after a first `pending()`;
- `next(Infinity)` works on a fresh iterator (it threw "datatype mismatch");
- a search over several root tables (a polymorphic schema), a sorted `all()` included, is ordered across the tables by its sort and then by key, and a key present in more than one of them is returned once;
- `markYielded` matches a row by its key as stored: a mark of an integer key takes its row whether the key is given as a number or as a bigint, and so does a mark of a string with a lone surrogate (stored with U+FFFD), and a mark that arrives while a call runs takes its row out of that call's result;
- on Node 22, a string with a lone surrogate (an unpaired UTF-16 code unit) is now stored with U+FFFD in its place, as on Node 24 and in the browser. better-sqlite3 stored the surrogate's own three bytes on Node 22, which read back as three U+FFFD, so an iterator could not find such a row again by its key. A row stored that way by an earlier release is no longer found by the original string, as on Node 24. Iterators that list keys do not return it either, and pages in primary-key order return it but then skip any key that sorts between its stored bytes and the three U+FFFD it reads back as, such as the same string with one U+FFFD.

The rest of the mutable iterator contract is unchanged: rows inserted or moved behind the cursor come at the front of the next call, an exhausted iterator sees later writes, `pending()` counts the rows still to come, and `close()` with a call in flight behaves as before.

A key list costs memory and time per open iterator: each iterator that lists keys holds its own list until it is done, closed or expires, and on Node the listing runs synchronously in better-sqlite3, so it holds the event loop meanwhile. After one write, 20 open iterators over 100,000 rows with 46-character keys held 7.3 MB each (147 MB in all, against 0.5 MB before this release), and listing their keys took about 23 ms each. A budget per database that drops idle key lists is planned.
