Start the reconnect entry inventory pass only when a transport returns under a topic session whose peer replication-info Full had already committed. A session whose Full has not committed yet no longer starts it at its stream-ready edge: a reconnect that renews the topic session, the first connection to a peer, and the first connection after a local restart. On a renewed session the pass ran on at most one side, depending on which side's stream became writable first, and walked every entry the peer leads after a one-second retry. These sessions now rely on their own Full: membership-driven repair when it changes the peer's ranges, and the unchanged-Full repair when it changes nothing. Reconnects under a settled session keep the pass as before.

The unchanged-Full repair now also runs for a peer's first session after this node restarts on persisted state. The peer's ranges survive in the replication index, so its first Full changes nothing, yet entries written just before the restart may never have reached it. A first session's known-peer marks can only come from what the peer sent since this node opened, so its repair honours them: each such reopen sends the peer one offer and, about a second later, pushes the entries the peer leads that it has neither confirmed nor sent to this node since the reopen, and the delayed sweeps resend only entries still unconfirmed. A peer does not answer an offer of entries it already holds, so after a restart that push can still carry most of what the peer leads: in a local measurement with small entries, 3.1 MB for 9,000 entries and 9.1 MB for 27,000.

Because renewed sessions no longer start the pass, a peer that comes back with an identical range after a departure this node missed relies on the unchanged-Full repair, which bypasses the peer's known-peer marks because they may belong to its previous process. Two things could drop that bypass before the entry went out: another dispatch to the peer that honours marks, such as an append backfill, cleared a marked entry from every repair frontier, so the repair's frontier emptied and dropped its bypass; and an older frontier for the peer that emptied before the repair's sweep queued anything took the bypass with it. A known-peer mark now retires an entry only from frontiers that honour marks, so the repair's frontier, like churn's, keeps the entry until the peer confirms it or this node no longer holds it, and the repair's sweep carries the bypass to the entries it queues. As in the previous release, while a renewed session's repair still waits for a confirmation, each of its four delayed sweeps sends every entry the peer leads again, confirmed or not.

No wire, option or public API changes.
